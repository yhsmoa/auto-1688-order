## 0. 공통 원칙 (운영 중 프로그램)

1. **동작 변경은 플래그 뒤에 넣고 기존 경로를 폴백으로 유지**한다. 플래그는 코드 상단 상수 하나로 끄고 켤 수 있어야 한다.
2. **판정은 항상 "읽어서 확인한 값"으로** 한다. 입력했다고 성공으로 치지 않고, 입력 후 다시 읽어 비교한다.
3. 실패는 **구체적 사유 문자열**로 남긴다 (실패V2 → `ft_order_items_failed.fail_reason` 으로 그대로 흘러가 재주문 카트의 근거가 된다).
4. 항목마다 **수동 검증 시나리오**를 먼저 통과시킨 뒤 배포한다. 돈과 직접 연결된 2번(차감)은 샘플 엑셀로 자동 테스트까지 둔다.
5. 항목별로 커밋·버전을 분리해 문제가 생기면 그 항목만 되돌릴 수 있게 한다.

## 1. 재고 제한(예: 2개)인데 주문 성공으로 표시되는 문제

### 현상과 원인
- `processGroupOrder` (automation.js:683~)는 옵션 행의 수량 입력칸에 `fill('') → type(qty) → Tab` 후 **다시 읽지 않는다**. 1688은 재고보다 큰 수량을 넣으면 입력칸 값을 재고 수(예: 2)로 **조용히 바꾼다**. 반대로 최소 주문량(起批量)보다 작게 넣으면 위로 올린다.
- 이후 `加采购车` 클릭 → `加购成功` 모달이 뜨면 그룹 전체를 `success` 처리한다 (automation.js:950~). 모달은 "담기 성공" 의미일 뿐 수량 보장이 아니다.
- 결과: 화면에는 성공, 장바구니에는 2개. 검수의 수량 비교에서야 드러난다.

### 수정안
automation.js `processGroupOrder` 수량 입력 직후:

1. **읽어서 확인**: `const applied = parseInt(await inputField.inputValue(), 10)`. `applied !== item.quantity` 이면 클램프로 판정.
2. **사유 문자열**:
   - `applied < requested` → `재고 부족 (요청 N / 가능 M)`
   - `applied > requested` → `최소주문 M개` (기존 실패 사유 표기와 동일)
   - 보조 정보: 옵션 행 텍스트에서 `(\d+)\s*件可售|库存\s*(\d+)|起批` 패턴을 뽑아 로그에 남김 (판정에는 쓰지 않음, 셀렉터 변동 리스크 때문).
3. **처리 정책 (Q1 결정)**:
   - **(A) 실패 처리 — 제안**: 해당 행 수량을 `0` 으로 되돌리고(`fill('0')` + Tab) 다시 읽어 0 또는 빈값인지 확인. 확인되면 `optionSelected=false`, `onProgress({status:'error', errorReason})`. 되돌리기 확인에 실패하면 **그룹 전체를 실패 처리하고 加采购车 를 누르지 않는다** (잘못된 수량이 담기는 것보다 안전).
   - (B) 부분 성공: 가능 수량으로 담고 `status:'success'` + 경고 표시. 검수에서 수량 불일치로 걸리고 사용자가 수동 반영.
4. 같은 그룹의 다른 옵션은 영향 없이 계속 진행 (현재 구조 유지).
5. `processOneOrder` (automation.js:339)는 호출처가 없는 **죽은 코드** — 같은 수정을 두 군데 하지 않도록 제거.

### 영향 범위
- renderer.js `onProgress` 핸들러(2290~)는 `errorReason` 을 그대로 표시하므로 변경 없음.
- 실패V2 내보내기(3885~)는 `order.reason` 또는 비고를 `fail_reason` 으로 저장 — 자동 실패 사유도 그대로 흘러가는지 확인 후 필요하면 `errorReason` 폴백 추가.

### 검증
- 재고가 적은 상품 1개로 수량 초과 입력 → 실패 사유 표기 확인, 장바구니에 담기지 않음 확인.
- 최소주문량 있는 상품 → `최소주문 N개` 사유 확인.
- 정상 상품 → 기존과 동일하게 성공.

## 2. 차감 엑셀에 여러 주문이 섞여 있을 때 해당 주문건만 처리

### 현재 동작
- `deductParser.parseDeductWorksheet` 는 AD열(买家留言)에서 주문코드를 모으고 **2개 이상이면 예외**로 중단한다 (deductParser.js:98~).
- AD열은 **1688 주문(A열 订单编号) 단위 병합셀**이다. 즉 주문코드는 1688 주문 단위로 붙어 있고, 상품 행 단위가 아니다. 같은 1688 주문의 2번째 행부터는 AD가 비어 있다(샘플 파일에서 확인).
- 메모는 참조코드 입력 시 `주문코드 | 날짜 | 품번:수량` 을 **줄바꿈으로 여러 줄** 넣을 수 있다 (automation.js 2709~). 지금 파서는 `split('|')[0]` 로 **첫 줄의 코드만** 읽으므로, 한 1688 주문에 두 코드가 섞인 경우를 놓친다.

### 분류 기준 제안 (3단계)

**1차 — 1688 주문 단위 분류 (필수)**
- A열 병합 그룹 = 1688 주문 1건. 그룹의 AD 텍스트 전체에서 `OR[A-Z]+\d{6}-[A-Z]\d{2}` 를 **모두** 추출해 코드 집합을 만든다.
- 대상 코드 = 현재 세션의 주문코드 (`collectCurrentOrderCodes()`, 정확히 1개여야 함. 2개 이상이면 중단).
- 그룹 분류:
  | 코드 집합 | 처리 |
  |---|---|
  | `{대상}` | **포함** |
  | 대상 없음 (다른 코드만) | **제외**, 코드별 건수 집계 |
  | 비어 있음 (메모 없음) | **제외**, 건수 집계 (1688 수기 주문 등) |
  | 대상 + 다른 코드 (혼합) | **Q2 결정** — 제안: 중단 + 목록 표시. 배송비(G)·실결제(I)가 주문 단위라 코드별로 정확히 나눌 수 없음 |

**2차 — 주문번호 등록 데이터와 교차검증 (강력 권장)**
- 주문번호 등록 단계에서 `orders[].dbData['1688_order_id']` 에 1688 주문번호가 들어간다 (renderer.js 2416~).
- `포함된 A열 집합` 과 `세션의 1688_order_id 집합` 을 비교:
  - 세션에는 있는데 엑셀에 없음 → 경고 "엑셀에 빠진 1688 주문 N건" (차감 누락 위험)
  - 엑셀에는 포함됐는데 세션에 없음 → 경고 "주문목록에 없는 1688 주문 N건" (코드 오기재 위험)
  - 주문번호 등록을 건너뛴 세션(집합이 비어 있음)은 검사 생략하고 그 사실을 확인창에 표시.

**3차 — Offer ID 교차검증 (보조)**
- 포함 그룹의 모든 행 Y열(Offer ID)이 세션 주문의 offer_id 집합에 속하는지 확인. 아니면 경고만 (차단 아님).

### 합산 규칙 (포함 그룹에 한정)
- G(운임)·I(실결제): 병합 첫 행에서만 (기존 규칙 그대로)
- U(수량): 포함 그룹의 전 행
- A(1688 주문번호): 포함 그룹의 고유값 → `order_no_1688`
- 계산식·반올림·검증(음수/0)은 변경 없음.

### 코드 변경
- `deductParser.js`: 반환값에 `included1688: string[]`, `excluded: { byCode: {코드: 건수}, noMemo: 건수 }`, `mixed: [{orderNo, codes}]`, `crossCheck: {...}` 추가. 입력 `opts` 에 `session1688OrderIds: Set`, `sessionOfferIds: Set` 추가. `excelOrderCodes.size > 1` 예외 제거 → 분류로 대체. 혼합은 정책에 따라 예외.
- `renderer.js processDeductExcelV2`: 확인창에 분류 결과 표시 —
  `포함 1688주문 N건 / 제외 M건 (ORBO…-R22 3건, 메모없음 2건) / 교차검증: 일치` 처럼. 경고가 있으면 빨간 줄로 표시하고 두 번 확인.
- 2차 교차검증 결과는 콘솔과 확인창 모두에 남긴다.

### 테스트 (node 스크립트, `test/deductParser.test.js` 신설)

## 3. 주문 성공인데 검수에서 "카트에 없음" (실제로는 있음)

### 원인 가설과 근거
1. **장바구니가 크면 DOM에 전부 렌더링되지 않음 (가장 유력)**
   - 10/25 검수 캡처: `cart.1688.com/ajax/quickCartCount.jsx` 응답 `sumOfKind: 200` — 장바구니에 200종.
   - 현재 흐름: 끝까지 스크롤(`smoothScrollToBottom`) → **맨 위로 스크롤** → `extractCartData` 로 DOM 1회 파싱. 목록이 lazy-load/가상 스크롤이면 위로 올라간 시점에 아래쪽 항목이 DOM에서 빠질 수 있다.
   - 추출된 수를 전체 종류 수와 비교하는 검사가 없어 누락을 모른다.
2. **offer_id 추출 실패로 항목이 조용히 버려짐**: `extractCartData` 는 `a[class*="title"][href*="detail.1688.com/offer/"]` 를 못 찾으면 `return` (automation.js 1878). 링크 클래스가 다른 항목은 사라진다.
3. **offer_id 불일치**: 주문 시 URL의 offer_id 와 1688 이 리다이렉트한 최종 offer_id 가 다를 수 있다. 검수는 주문 URL 기준으로만 비교한다.

### 수정안 — Phase 1 (DOM 방식 보강, 바로 적용)
1. **완전성 검사**: 추출 후 `quickCartCount.jsx` (`sumOfKind`) 또는 하단 바의 종류 수를 읽어 `DOM 추출 수 < 전체 수` 면 추가 스크롤 + 재추출(최대 3회). 끝내 미달이면 검수 결과 배너에 `장바구니 N종 중 M종만 확인 — "카트에 없음" 판정은 재확인 필요` 표시하고, 미달 상태의 "카트에 없음"은 `error` 대신 `unknown`(회색)으로 표시 (Q3).
2. **스크롤 중 누적 추출**: `smoothScrollToBottom` 의 각 스냅샷 시점에 `extractCartData` 를 돌려 `offerId|color|size|sellerName` 키로 병합. 가상 스크롤이어도 전 구간을 지나며 모두 모인다. 체크 상태는 마지막 값으로 갱신.
3. **offer_id 폴백**: 제목 링크가 없으면 item-group 안의 어떤 `a[href*="offer/"]`, 이미지 링크, `data-offer-id` 속성 순으로 시도. 끝내 없으면 버리지 말고 `offerId:''` 로 남겨 "식별 불가 항목 N개" 로 보고.
4. **최종 offer_id 기록**: `processGroupOrder` 에서 `page.goto` 후 `page.url()` 의 offer_id 가 주문 URL과 다르면 `onProgress({index, canonicalOfferId})` 로 전달. 검수 매칭(`compareOrdersWithCart`)은 원본·최종 둘 다 허용.
5. 로그: 추출 수 / 전체 수 / 재시도 횟수 / 식별 불가 수를 매 검수마다 남긴다.

### Phase 2 (네트워크 기반 검수, 조사 후 결정)
- 장바구니 페이지는 `mtop.1688.buycenter.mtoppurchaseastoreservice.render` (초기, 286KB) / `.async` (全选 후, 300KB) / `.asyncload` 로 데이터를 받는다. `data.model` 안에 `item_group_<offerId>`, `cartIds` 가 있어 **전 항목이 들어 있을 가능성**이 높다.
- 현재 캡처는 미리보기 1,500자만 저장해 구조를 확정할 수 없다 → 캡처를 render/async 본문 전체 저장으로 확장(1~2회 검수 분) → 구조 분석 → API 모델에서 `offerId/옵션/수량/체크` 를 뽑는 추출기를 만들어 DOM 결과와 **병행 비교**(불일치 로그) → 안정되면 전환.

### 검증
- 장바구니 150종 이상 상태에서 검수 → 추출 수 == 전체 수, "카트에 없음" 0건 확인.
- 의도적으로 주문 URL을 구 offer_id 로 넣은 상품 → 최종 offer_id 로 매칭되는지.

## 4. V2 참조코드 — 처음 오래 기다리고 하나씩 입력하는 문제

### 현재 타임라인 (automation.js `inputRefCodesV2`, 반복 1회 기준)
| 구간 | 현재 | 비고 |
|---|---|---|
| 카트 이동 후 고정 대기 | 5초 | 조건 없이 대기 |
| 全选 체크 폴링 | 최대 30초 | 상점 전부 checked 될 때까지 |
| 결산 버튼 활성 폴링 | 1초 단위, 최대 30초 | |
| 주문확인 페이지 고정 대기 | 2초 | |
| 데이터 수집 (Phase 1) | 1회 왕복 | 이미 일괄 처리됨 |
| **textarea 입력 (Phase 3)** | 주문마다 scroll + 300ms + click + 200ms + fill + 300ms + 읽기 | **주문 24건이면 약 25~30초, "하나씩" 보이는 구간** |
| **빈 textarea 검사 (5.5)** | 주문마다 2~3회 왕복 | 24건이면 수 초 |

### 수정안
**1단계 (안전, 바로 적용)**
- Phase 3: 주문마다 넣던 `scrollIntoViewIfNeeded / click / waitForTimeout` 제거. Playwright `fill()` 만 순서대로 실행 (fill 은 포커스·이벤트를 자체 처리, 1건 50~100ms). 24건 ≈ 2초.
- 5.5 빈칸 검사: 모든 textarea 값을 **1회 `page.evaluate`** 로 읽어 판정 (왕복 24→1).
- 고정 대기 → 조건 대기: 카트 5초 → `shop-container 수가 2회 연속 동일 + 하단 바 표시`; 주문확인 2초 → `textarea 수 == .order-inner 수`.
- 예상: 반복 1회당 입력 구간 25~30초 → 3초 내, 대기 구간 7초 → 보통 2~3초.

**2단계 (플래그 `REFCODE_BATCH_FILL`, 기본 off → 드라이런 통과 후 on)**
- 모든 textarea 를 **1회 evaluate** 로 채움: native value setter 로 값 설정 + `input`/`change` 이벤트 dispatch. 이어서 1회 evaluate 로 전체 값 읽어 비교, 불일치 건만 `fill()` 폴백.
- 리스크: `q-textarea` 는 커스텀 컴포넌트라 프로그램 입력을 내부 상태에 반영하지 않을 수 있다. DOM 값이 맞아도 제출 시 메모가 비어 갈 가능성이 있어 **읽기 검증만으로는 부족**하다.

## 8. 2026-10-25 답변 반영 (아래가 위 본문보다 우선)

### 1번 — 합산 구조를 반영한 재고 클램프 처리 (확정 방향)
- 같은 상품·같은 옵션의 행들은 `groupOrdersByOfferId` 가 수량을 합산해 1회 입력하므로, **행 단위 배분**으로 처리한다.
  1. 합산 N 입력 → 읽어서 실제 M 확인.
  2. M < N: 구성 행을 순서대로 보며 "행 수량 전량 수용 가능하면 포함" (행 분할 없음). 예) 2,2,2 / M=5 → 2행 포함(4), 1행 제외, 1개 미사용.

### 1번 추가 — 주문 단위(5·10 배수)·최소주문량까지 포함한 수량 확정 알고리즘
입력값 N 과 읽은 값 R 의 관계로 분기한다. (셀렉터로 재고/단위 텍스트를 읽는 것은 로그용일 뿐, 판정은 항상 R 로)

| R vs N | 의미 | 처리 |
|---|---|---|
| R == N | 정상 | 성공 |
| R == 0 | 품절 | 그룹 전부 실패 `품절` |
| R < N | 재고/구매 제한 (단위 내림 포함) | **행 단위 배분 (아래)** |
| R > N | 최소주문량 또는 단위 올림 | **정책 Q (아래)** |

**행 단위 배분 (R < N)**
1. 구성 행을 표 순서대로 두고 k = 전체 행 수 − 1 부터 1 까지 내려가며 앞 k 행 합계 S_k 를 **실제로 입력하고 다시 읽는다**.
2. 읽은 값 R' == S_k 이면 확정: 앞 k 행 성공, 뒤 행 실패 (`재고 부족 (가능 R / 요청 N — 이 건 q개 제외)`).
3. R' ≠ S_k 이면 k 를 줄여 반복 (단위 상품에서 S_k 가 배수가 아니면 바뀌므로). 시도 횟수 상한 6회. 끝까지 불일치 → 그룹 전부 실패 `단위/재고 제약으로 요청 수량 구성 불가 (가능 R)`.
4. R' > S_k (올림) 가 나오면 아래 정책 Q 를 그대로 적용.
5. 최종 확정 후 반드시 한 번 더 읽어 입력칸 값 == 확정 수량 확인 후 加采购车.

**정책 Q (R > N, 요청보다 많이 담김)** — 미결정
- (a) 제안: 그대로 담고 성공 처리 + 행 경고 `⚠ R개 담김 (요청 N, 단위/최소주문)` → 검수 수량 불일치에서 사용자가 반영/취소 결정 (현재 동작과 동일, 정보만 추가).
- (b) 실패 처리 `단위 X개 (요청 N)` (기존 `최소주문 2개` 사유와 같은 방식).

**검수 정합성**: 실패 처리된 행은 자동 취소 사유가 붙어 검수 합계에서 빠지고, (a) 로 담긴 초과분은 검수에서 수량 불일치로 표시된다. 실패V2 내보내기의 `fail_reason` 으로 그대로 전달된다.

### 2026-10-25 3차 — 수량 확정 규칙 최종 (정책 Q 폐기, 아래로 대체)
- 원칙: **요청보다 많이 담지 않는다.** 행들을 합쳐 1688이 그대로 받아주는 수량이 되는 조합만 성공.
  - 예) 단위 5: 5,3,3 → {5} 만 성공 / 5,3,2 → 10 전부 성공 / 3,4,2 → {3,2}=5 성공, 4 실패 / 최소주문 2: 1,1 → 둘 다 성공.
- 절차 (입력값이 바뀐 옵션에서만 수행, 정상 옵션은 읽기 1회만 추가):
  1. 제약 파악: `1` 입력→읽기(최소주문량 m), `m+1` 입력→읽기(단위 u = 차이), 전체합 입력→읽기(상한 M).
  2. 조합 계산: 행 부분집합 중 합계 S 가 `S ≥ m`, `S % u == 0`, `S ≤ M` 인 것. 선택 기준 ① S 최대 ② 동점이면 표 순서 앞 행 포함 조합.
  3. 선택 S 입력 → 읽기 == S 일 때만 확정. 불일치면 다음 후보 (최대 6회). 후보 없음 → 전부 실패.
  4. 확정 뒤 입력칸 재확인 후 加采购车. 포함 행 성공, 제외 행 실패 + 자동 취소 사유 `단위 u개·재고 M — 조합 불가 (요청 q)` / 품절 `품절`.
- 속도: 정상 옵션 +0.05초, 제약 옵션 +1.5~2초. 입력 간격 0.3초 유지, 입력에도 봇 챌린지 감지 적용.
- 합산 방식 확인: 같은 옵션 행은 Node 에서 미리 합산해 **한 번 입력**, 상품당 加采购车 1회 — 현 구조 유지.

### V2 참조코드 '클릭됐는데 안 넘어가고 완료로 끝나는' 문제
- 원인: 结算 클릭 후 대기하던 URL 패턴 `**/order/confirm*` 이 실제 주소(`smart_make_order.htm`)와 달라 매번 실패 → 경고만 찍고 진행. 실제로 카트에 머문 경우에도 뒤 단계(주문 0건·빈칸 0건·주소 없음·배송방식 없음)가 빈손으로 통과하다 제출 버튼 30초 대기 실패로 break → 화면에는 "V2 참조코드 입력 완료!" + 종료 사유가 떠서 완료로 보였음.
- 수정: ① 结算 클릭 후 주문확인 페이지 진입(URL + .order-inner)을 확인, 안 넘어가면 버튼이 0.5초×2회 연속 활성일 때 재클릭(최대 3회), 실패 시 중단 ② 주문확인 페이지에 주문 블록 0이면 중단 ③ 提交订单 클릭은 MutationObserver 로 loading/disabled 전환·버튼 사라짐·URL 변경을 8초 감시 → 신호 없으면 '제출 안 됨'으로 중단(이중 주문 위험 때문에 자동 재클릭 안 함), 신호는 있는데 40초 안에 성공 페이지 미확인이면 성공 처리 없이 기록, 연속 2회면 중단 ④ 화면 안내문(토스트·다이얼로그)을 사유에 포함 ⑤ 결과 알림: 정상 종료만 "✅ 완료", 나머지는 "⛔ 중간에 멈췄습니다(완료 아님)" + 사유 + 미확인 묶음 수. 참조코드 단계 완료 표시도 정상 종료일 때만.
